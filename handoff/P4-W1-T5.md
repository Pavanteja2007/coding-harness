## 3. The store's contract, in one table

T1 owns the document; T5 owns the seal. The two are deliberately **not** merged.

| path | owner | mutable | why |
|---|---|---|---|
| `features.json` | T1 writes / T5 reads | obligations only | the agent's declarations |
| `PROGRESS.md` | T1 writes | append-only | human-readable ledger |
| `features.seal.json` | T5 | **no** | fingerprint of the OBLIGATIONS |
| `.neo-store/history.jsonl` | T5 | append-only | chained status history |
| `.neo-store/evidence/<sha256>.json` | T5 | content-addressed | run evidence, deduplicated |
| `.neo-store/quarantine/<ts>/` | T5 | no | corruption moved aside |

Writable feature fields: `status`, `evidence`, `sessions_touched` — nothing else.
`AGENT_WRITABLE_LEDGER_FIELDS` is **imported from T1** and asserted to *be* T1's
tuple, and `FL.ALLOWED_TRANSITIONS` is pinned equal as a set to
`LH.FEATURE_STATUSES`. Two copies of a vocabulary is how a fifth status appears
that no verifier knows about.

### The seal covers the obligation and NOT the report

`ledger_projection()` hashes only immutable fields. A guard that fingerprinted
`status` would make honest progress reporting a seal violation; one that
fingerprinted nothing would catch no tampering. Both halves are pinned,
including the negative one (a projection that leaked `status` fails).

## 5. The multi-session evaluation — and its largest gap, stated plainly

### What is real and under test

`build_session_brief` reads only `init.sh`, `features.json`, `PROGRESS.md`, the
request and the constraints. It holds **no message list**. A marker planted
exclusively in session 1's conversation is asserted absent from session 3's
brief. **The survival-vs-compaction distinction is genuinely under test.**

### What is not, and this is the hand-off's most important line

The session body is `_scripted_session`, which writes the feature's
implementation directly and verifies it through the injected gate. It **does not
call `harness.agent_loop.run_agent`**, and `session_turns` is **recorded rather
than enforced** — nothing reads it. The task is multi-session because the
*runner assigns one feature per session*, not because a session ran out of turns.

My first draft's docstring claimed otherwise ("a session here is a fresh
`run_agent` call", "its turn budget is `session_turns`, which is the whole
mechanism"). I found it while assembling this hand-off, fixed the prose, and
added `TestTheModuleDoesNotClaimMoreThanItDoes` to hold it to the truth in both
directions — the module may not advertise a real agent session it does not make,
and may not quietly drop the limit sentence if it starts making one.

### The consequence, measured and published

```
metrics_that_vary == ["parent_context_tokens", "tokens_per_session"]
completion           varies: False
rework_rate          varies: False
constraint_retention varies: False
```

The two that vary are the initializer's brief being genuinely longer — a real
measurement, reported as one. **None of the three outcome metrics move**, and
those are the ones the four arms exist to move. `read_before_edit` and
`subagent_isolation` set mechanism keys the scripted body never exercises, so
they are structurally incapable of separating today. A pin asserts this exact
split, so the day an outcome metric separates it fails loudly instead of being
quietly reported as a result.

### The honest successor

Drive real bounded `run_agent` sessions with a real turn ceiling. That is what
would let the four arms separate. It is not built, and nothing in the current
code pretends it is.

## 9. Two things I got wrong and fixed — please read both

### 9a. I ran `ruff --fix` on whole directories and edited other terminals' files

`python -m ruff check --fix tests/ evals/` applied 34 fixes across 11 files T5
does not own (`tests/test_cli*.py`, `tests/test_command_routing.py`,
`tests/test_dashboard.py`, and others), stripping imports and reordering import
blocks. That violates the "must not edit another terminal's files" constraint.

**Fixed:** reverted all 11 with `git checkout --`, then re-ran their suites to
confirm the revert was lossless — **341 passed in 407.19s**. Nothing depended on
the removals.

**Consequence you should know about:** `ruff check tests` now reports 50 errors,
of which ~46 are in exactly those reverted files. That is the tree's real state,
not something I introduced, and it is another terminal's to resolve. Evidence
that `tests/` was already lint-dirty before I touched anything:
`tests/test_p3b_w2_truth.py` (4) and `tests/test_capability_surface.py` (1)
carry findings I never introduced and could not auto-fix.

I also fixed one genuine defect in a file my terminal *does* own from a previous
round: `evals/tools_ablation.py` was missing `Tuple` from its `typing` import
(4 × `F821`). It was masked by `from __future__ import annotations` at runtime
but would have raised under `get_type_hints()`.

### 9b. A pin I wrote for a closing gap told me the gap had closed

`ALLOW_ATTESTED_IS_A_DEAD_ESCAPE_HATCH` was my own finding in T1: an `attested`
verification was normalised to `ran=False, outcome="not_run"`, so
`allow_attested=True` could never satisfy pass evidence and a `human_check`
feature could not reach `passing` at all. **T1 fixed it mid-phase**, and the
inverted pin failed on arrival — which is what a pin for a closing gap should do.

I then **deleted** the entry from `FL.RECORDED_GAPS` rather than flipping it to
"closed", and pinned the surviving two-sided rule: an attestation passes **with**
the flag and is refused **without** it. `RECORDED_GAPS` is now the empty tuple
and that emptiness is asserted. A registry that keeps reporting closed gaps
teaches the next reader to ignore the registry, which costs more than the gap
did.
