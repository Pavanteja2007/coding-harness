## 5. THE FIVE-STATE DEFINITION

`execution.e2e_verify.E2E_STATES` — a **closed five-value vocabulary**. Four
describe a *measurement*; the fifth describes the **absence of a usable one**.

| state | meaning | settled? | `passed`? |
|---|---|---|---|
| **`passed`** | the check ran and the feature behaved | yes | **yes** |
| **`failed`** | the check ran and the feature did not behave | yes | no |
| **`blocked`** | the check **could not run**, with a mandatory reason | no | no |
| **`not_run`** | the check was **not attempted** (no declaration, or the run policy said not to) | no | no |
| **`untrustworthy`** | **Wave 2.** the check ran (or could have) and its verdict is **VOID IN BOTH DIRECTIONS** — not a passing feature and not a broken one | **no** | no |

### The argument for the fifth state, in one paragraph

Its whole case is one sentence: **the check ran, exited 0, and asserts nothing.**
That is not `passed` — reporting it as `passed` converts an honest gap into a
false pass, which is the specific failure this project exists to prevent. It is
also not `failed`, because nothing was shown to be broken and a ledger that
renders it `failed` sends a repair loop after a working tree. So it is a third
thing, and it **dominates the report verdict**.

### Why it dominates

`E2EReport.verdict` checks `untrustworthy` **first**. Ranking it below `passed`
would let a report containing one green row and one void row read `passed` —
precisely the false pass the mechanism exists to prevent. Ranking it below
`failed` would send a repair loop after a working tree. **Both are the same
mistake in opposite directions: letting a void measurement inherit a decision
that was never made.** Pinned over **every 2-combination of the five states**.

### Two refusals that keep the state honest

1. `E2EResult` **REQUIRES a reason** on every `untrustworthy` row. A state that
   means "this measurement is void" must say why, or it is an unexplained
   refusal and a reader cannot tell it from a bug.
2. `E2EResult` **REFUSES a trust receipt on any other state.** A trust field
   that can appear on a green row teaches every reader to skip it, which is the
   one outcome it exists to prevent.

### What produces it

`execution.e2e_trust` answers three questions, and each maps to attack rows:

| question | rows | the decision |
|---|---|---|
| **OWNERSHIP** — is this check the repository's own? | 1, 2, 3 | `assess_ownership` → `OwnershipVerdict` |
| **STRENGTH** — can this check decide anything? | 4 | `assess_strength` → `StrengthVerdict` |
| **TIMING** — did it run for a plausible amount of time? | 6 | `assess_fast_pass` → `FastPassVerdict` |

folded by `assess_check` into `TrustVerdict`, converted by
`e2e_trust.gate_e2e_result`, and constructed by
`e2e_verify.untrustworthy_result`.

**The one rule that is a refusal:** `gate_e2e_result` rewrites `passed` and
**nothing else**. A `failed` from a weak check passes through, because a failing
weak check is still evidence that something is wrong and turning it into a
meta-problem would hide a real signal behind it.

## 6. THE PER-SESSION COST TABLE + POLICY

Every row is **read from `execution.verify_cache.COST_TABLE`** — delegated, not
copied. This repository has shipped six second authorities for a question
somebody else already answered and every one of them drifted; a seventh would be
the seventh.

| row | measured | basis |
|---|--:|---|
| `verification_cold` | **9.23 s** | first `verify()` on a cold image cache, dependency-image build included |
| `unit_verification_warm` | **6.49 s** | median of 3 warm cycles |
| `e2e_single_check` | **1.61 s** | one declared e2e check end to end |
| `sandbox_cold` | **1.59 s** | summed per-call sandbox overhead |
| `sandbox_warm` | **1.59 s** | the same, warm (the image build happens inside `ensure_image`, before the timed call) |
| `cache_lookup` | **3 ms** | median of 200 pairs over a populated cache — ~1e-4 of the verification it can save, so a lookup can never cost more than the thing it saves |

`cache_lookup` renders as **3 ms, never `0.00s`** — a real 3.20 ms printed as
`0.00s` is the same string a genuinely free operation produces, on the one row
whose entire purpose is to show a lookup is cheap but not free. A pin asserts
`"0.00s" not in render_cost_table()`.

An unmeasured row stays `None` and renders `UNMEASURED`. **A cost table
populated from a run that failed is a receipt with no measurement in it.**

### The run policy

```
unit_verification : every iteration of the inner loop, and once per session   [ALWAYS]
e2e               : on_demand (the shipped default), plus the final gate       [ON_DEMAND]
reuse             : content-addressed only; a partial match is refused        [CONTENT_ADDRESSED_ONLY]
```

**N sessions:** verification is PER SESSION, never per iteration beyond the
inner loop, because a session is the unit over which a content digest changes;
the cost to amortise is the one-time image build, and paying it per iteration
multiplies a one-off by the iteration count for no extra signal.

**`unit_verification` is NEVER skipped.** Every knob is about **WHEN** a check
runs, never **WHETHER**. Skipping verification is how a project rots quietly. A
pin asserts both the `ALWAYS` verdict and the rendered sentence.

### The measurement that contradicts the old justification — and is published anyway

The e2e roll-off multiple is **DERIVED** from the two measured rows, not
asserted: **1.61 / 6.49 = 0.25×**, i.e. **an e2e check is CHEAPER per call
than one warm unit verification** on this fixture, because a unit verification
pays for **two** container calls (a target run and a full-suite run).

Wave 1 justified `on_demand` partly on cost ("one to two orders of magnitude
above"). **That number does not exist.** The policy is therefore re-argued from
what the measurement supports — e2e can only run where a server exists, and a
per-iteration e2e would multiply a check whose signal changes only when
behaviour changes — and the contradiction is printed in the receipt rather than
smoothed over.

### Coverage, and reuse — both reported, never assumed

* **Coverage is DELEGATED** to the selector's own `coverage_is_complete()` and
  `coverage_is_sound()`, and the two are **conjunctioned**. `fallback_all`
  selects everything and is therefore COMPLETE while being **UNSOUND**; only the
  conjunction may sit beside a passing claim. Zero coverage is `not_run`, and the
  coverage vocabulary is **disjoint from the state vocabulary**.
* **Reuse requires all THREE groups** — source digest, declaration digest,
  environment fingerprint — and a **partial match is refused, naming the group
  that failed**. An empty expected digest is **not a wildcard**.
* **The rate reports BOTH numbers**: `reuse_rate` (the flattering one) and
  `reverified_rate` (**the honest one**), because a summary carrying only the
  first answers the vendor's question while the reader is asking "how much did
  you actually check?"

**Four things T5 must not do, and each is a refusal rather than advice:**

1. **Do not read `rows[*]["state"] == "passed"` as "the feature works".** Read
   `ledger.provable`. A green row beside a void row reads `passed` at the row
   level and `untrustworthy` at the report level, and the row level is the one
   that gets scanned.
2. **Do not treat a reused row as evidence.** `may_mark_feature_passing` is
   hard-coded `False` by the producer and `ledger_gate` refuses on
   `fresh_evidence`. Read `reuse.fresh_evidence`, not the row's shape.
3. **Do not accept evidence from another commit.** Call `assert_same_commit` and
   let it raise. There is no `force=`, deliberately.
4. **Do not render `coverage.fraction` without `coverage.verdict`.** A `0.0`
   beside a passing claim reads as "we ran everything and covered nothing".

(`result.e2e_evidence`), the `execution/flake_gate.py::attach_evidence`
precedent. **Consequence: `runtime/serialize.py` does NOT round-trip it, so a
replayed journal loses the evidence entirely** — and a ledger reading a replayed
journal sees *nothing* rather than "not measured". Persisting it is T5's call
and this round's request 6.

## 8. ANYTHING FOUND THAT NO PROMPT ANTICIPATED

### 8.1 🔴 TWO REAL BYPASSES in the test-removal guard

Found by driving the **real** `SafeToolBackend`, not by reading. Both were
ALLOWED, both are the same coverage removal as `unlink`, and both reached
through a door the command gate had no row for:

```
chmod 000 src/tests/test_checkout.py              -> refused=False  shape=ordinary_command
python -m pytest -q --deselect tests/test_a.py::test_a -> refused=False  shape=ordinary_command
```

`chmod_disabled` has been a **published shape since Wave 1** and the **bytes**
funnel catches it as a mode DELTA — but the **shell** is the only gate on a
`chmod`, because a mode change made by a command never reaches a workspace
method. And the module's own docstring *claims* a deselect is refused "on the
same path as `unlink`": it was, for the **config-file** route only.

Both closed. `COVERAGE_REMOVING_FLAGS` now carries a **third element** per row,
`needs_test_path`, because the two routes need different gates: `--ignore` names
a **path** and keeps the path gate (`--ignore htmlcov` must stay allowed), while
`-m 'not slow'` names **cases** and applying the path gate to it left it
allowed — which is how it stayed allowed through two rounds.

### 8.2 🔴 `_matches_builtin("pytest")` returned `True` — and it was invisible

A file named `pytest` is not a test file; the word is a **command**. So the
gate's own path-token reader classified
`python -m pytest -q --ignore htmlcov` as naming a test path and refused it.

**The false positive predates this round and was INVISIBLE**: nothing matched a
coverage-removing flag, so the buggy token was never consulted for a command
with no deletion shape. **Adding the deselect row made a long-standing reader
bug visible in one line.** That is the strongest argument in this handoff for
driving the **real classifier** rather than the real workspace.

### 8.3 The daemon's memory limit is 7.614 GiB, and 8 sessions over-commit it

`docker info` MemTotal is **8 175 947 776 (7.614 GiB)** — the Docker Desktop
**VM's** limit. The first version of the memory reader called a helper that does

broad `except`, and the axis reported the **Windows host's 15.72 GiB** as though
it were the limit a container is held to. The axis would have concluded "51%,

**At the default `mem_limit="1g"`, this host over-commits at 8 concurrent
